# Markdown — 落地细则

Source: <https://spec.commonmark.org/>
配套：markdownlint（规则检查）、Prettier 或 remark（格式化）、链接检查器；先以仓库 .markdownlint.* / .prettierrc 为准。

## 1 适用范围与优先级

- CommonMark 定义语法基线：块结构、行内结构、转义、硬换行、代码围栏。GFM 是 CommonMark 的超集，另有表格、任务列表、删除线、扩展自动链接、tagfilter。
- 两者都不规定行宽、目录、术语、语气。Google Markdown Style Guide、markdownlint 默认规则、Write the Docs 是社区/平台规范（**社区惯例，非官方规则**）。
- 适用对象：仓库内 README、设计文档、ADR、变更记录，以及 SKILL 与 agent 指令文档。
- 先确认渲染器再定规则：GitHub、GitLab、静态站点生成器、IDE 预览对脚注、数学公式、`[TOC]`、`details` 的支持并不一致，扩展语法以平台实测为准。
- 裁决顺序：仓库 `.markdownlint.*` 与渲染器实测行为 → 同目录既有文档 → Google Markdown Style Guide → markdownlint 默认值。
- 硬约束：源文件必须纯文本可读，不依赖渲染器私有语法表达结构；不得嵌入未审计的原始 HTML 与脚本。

## 2 缩进、行宽与排版

- 行宽 80（Google 与 markdownlint `MD013` 默认都是 80）。例外只有四类：链接、表格、标题、代码块——Google 明确豁免它们。
- `MD013` 默认会检查表格与标题，要得到上面的口径需在配置里关掉 `tables`、`headings`、`code_blocks`；以仓库配置为准。
- 缩进宽度只有两种约定：Google 的 4 空格（列表标记用 `- ` 时正文缩进 4 格，续行也 4 格），与 markdownlint `MD007` 的默认 2 空格。仓库必须二选一并写进 `.markdownlint.*`，同一仓库内不得混用。
- 不用行尾空格制造 `<br />`：预提交钩子与编辑器会自动清掉，硬换行改用行尾反斜杠。
- 禁止尾随空格（刻意的硬换行除外），禁止连续空行（`MD012` 默认最多 1 行），文件末尾单个换行（`MD047`）。
- 标题只用 ATX（`#`）形式，`#` 后必须有一个空格——CommonMark 规定 `#Heading` 不是标题，会被当正文。标题前后各一空行（`MD022`），标题不缩进（`MD023`）。
- 标题层级一次只降一级（`MD001`），单文档只允许一个 H1（`MD025`），标题不重复（`MD024`）。
- 强调用 `**` 与 `*`，不用 `__` 与 `_`：词内下划线与标识符、文件名冲突。同一文档风格一致（`MD049`/`MD050`）。
- 无序列表统一用 `-`（`MD004` 默认 `consistent`）；列表标记后留一个空格（`MD030`）。
- 表格前后各一空行（`MD058`），每行列数必须一致（`MD056`），管道风格统一为前后都有 `|`（`MD055`）。
- 代码围栏用三个反引号并标语言（`MD040`）；围栏长度必须大于内容里出现的围栏长度，嵌套代码示例时外层用四个反引号。
- 中文与英文、数字之间留一个半角空格；中文标点紧跟中文，不在标点内外侧塞 Markdown 语法标记。

## 3 命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 文件 | 小写 kebab-case，`.md` 结尾 | `getting-started.md` |
| 目录 | 小写 kebab-case，按功能分组 | `guides/`, `adr/` |
| H1 标题 | 名词性短语，与文件名语义对应 | `# Deploy checklist` |
| H2 / H3 标题 | 唯一且自足，脱离上下文仍可理解 | `## Retry policy` |
| 代码标识符 | 与代码完全一致，含大小写与连字符 | `maxRetries`, `--dry-run` |
| 产品 / 工具名 | 保持官方大小写 | `Markdown`, `GitHub`, `macOS`, `Ruby` |
| 术语 | 全文一个说法；首次出现给全称与缩写 | `Continuous integration (CI)` |
| 文件名禁用词 | 不用 `notes`、`misc`、`temp`、`final`、`new` | `design/cache-invalidation.md` |

- 标题唯一不是为了美观：重复标题会生成 `-1` 后缀锚点，站内链接随之失效（`MD051` 会报错）。
- 标题不带句末标点（`MD026` 默认禁止 `.,;:!` 与全角 `。，；：！`，问号默认放行）。
- 文件名不用大写、空格与下划线：URL、大小写敏感文件系统、锚点都会出岔子。
- 不用日期或版本号做文件名，它们一定过期；把适用范围写进正文或 front matter。
- 术语表放在 `docs/glossary.md` 或文末，替代表达写清，不做同义词轮换。

## 4 文件与模块组织

- 文档骨架固定顺序：`# 标题` → 1~3 句说明这篇文档解决什么问题 → 目录（长文档）→ 各 `##` 小节 → `## See also`。
- 一个文件一个主题；超过约 300 行按小节拆文件，拆分点落在标题边界而不是句子中间，父文档链接到子文档。
- 目录用链接列表实现，不用 `[TOC]` 指令：GitHub 不渲染它，只在自己确认支持的平台（如 Gitiles）上用。
- 仓库根 `README.md` 只回答四件事：是什么、怎么装、怎么用、细节去哪看；细则移入 `docs/`。
- 相对链接用相对当前文件的最短路径；跨多层目录时用仓库根绝对路径，避免 `../../../` 堆叠。
- 图片放 `docs/images/` 或与文档同目录，文件名与文档同名加序号；不引用仓库外的临时图床。
- 引用式链接定义放在首次使用处所在小节的末尾，多处使用的定义放文末，避免移动小节后出现悬空定义。
- SKILL 文档单独一套约束：`SKILL.md` 只做索引（约 100 行内），细则放 `references/`，避免加载时污染上下文；references 之间不互相转载同一段内容。
- 每个 reference 文件只讲一个主题，标题层级与同级文件保持一致，便于交叉引用。

## 5 文档结构与信息层级

- 每段一个论点，第一句给结论，后续给依据。理由：文档以扫读为主，只读每段首句的人也必须拿到信息。
- 句子控制在 20~30 字，一段 3~6 句；超过就拆段，并用小标题承接。
- 层级只有三层可用：标题、列表、正文。嵌套列表超过两层改用小标题，不要靠缩进表达层级。
- 列表用于并列项（每项一个概念）；表格用于真正的二维对照（至少两行两列且列值确实不同）；段落用于因果、条件与权衡。
- 表格单元格只放短语，超过一行的内容移到正文；单元格里塞长句会让整张表无法扫读。
- 行内代码用于文件名、命令、标识符、字面量；代码块用于多行命令、配置、输出。行内代码不会被渲染器改写，也不会被自动链接。
- 命令示例能直接粘贴就不加 `$` 提示符（`MD014`）；需要展示输出时才保留 `$`，并让输入与输出可区分。
- 关键结论不放进折叠区或引用块，折叠只用于补充材料；引用块用于注意事项，不用于正文论证。
- 易过期信息（版本、日期、环境差异）集中到文末的“适用版本”，正文只写稳定结论。
- 一篇文档只保留一个“为什么”，避免同一理由在多个小节反复重述；重复即删。

## 6 函数与 API 设计

- 描述函数先给签名原文（语言、参数、返回类型），再给一句话用途，最后给参数与返回值细节；读者先确认“是不是我要调的”。
- 参数按表列出：名称、类型、是否必填、默认值、取值范围。没有默认值的写“必填”，不留空格子。
- 返回值单独成段，说明成功值、空值语义与错误形态（抛异常、返回错误码、返回 `nil`/`None`）。
- 命令文档给完整可运行的一行命令，再逐个说明选项；选项顺序与 `--help` 输出一致。
- 代码示例必须可运行且上下文自足：包含必要的 import、前置条件、期望输出；省略部分用注释标明省略了什么。
- 示例输出与示例代码分开写在两个代码块里，不要用注释假装输出。
- 破坏性变更写清迁移方式：旧调用、新调用、需要改哪一行；只写“已废弃”没有信息量。
- 术语与签名大小写逐字复制，不改写成“更通顺”的形式；改名会导致复制粘贴失败。
- 一节只讲一个 API；多个相关 API 用表格做索引，详情各自成节。

## 7 错误处理

- 文档里的错误信息照抄程序原文，不润色；同时给一句人话解释和一个修复动作。理由：用户会拿原文去搜索。
- 每个“失败”小节写三件事：症状（用户看到什么）、原因、修复步骤；缺一项就无法自助排查。
- 链接失效按缺陷处理：合并前跑链接检查，锚点必须与标题生成的锚点逐字一致（`MD051` 按 GitHub 规则计算）。
- 内容过期按缺陷处理：代码示例跑不通、命令选项已改名、截图与界面不符，都必须在同一改动里更新或删除。
- 渲染差异要显式验证：表格、嵌套列表、脚注、数学公式在目标平台预览一遍，不能只在本地编辑器里看。
- 不写“如果出现问题”“在某些情况下”这类含糊条件；写触发条件，例如“当 `retries` 大于 0 且服务返回 5xx 时”。
- 已知限制单独成节并写影响范围；把限制藏在正文段落里等于没写。
- 删除比保留过期内容安全：无法确认是否仍成立的段落，删掉并在变更记录里说明。

## 8 并发、资源与生命周期

- 多人同时编辑同一文档时，按小节分工并提前约定标题结构，减少同一段落的并发改动。
- 重命名或移动文档必须在同一改动里更新所有引用：全文搜索旧路径与旧锚点，链接检查器必须为 0 断链。
- 文档有明确所有者（front matter 的 `owner` 或 CODEOWNERS），无主文档在评审时指定负责人。
- 废弃文档先标记（标题下加一行状态与替代链接），一个发布周期后删除，不做无限期保留。
- 文档与代码同仓同评审：接口改动、配置改动、行为改动必须在同一 PR 更新对应文档。
- 每次只改一个主题；纯格式修正与内容修正分开提交，避免 review 被噪声淹没。
- 大段删除前确认没有外部链接指向它；有外部引用时保留跳转页而不是直接删文件。

## 9 注释与文档

- Markdown 没有通用注释语法；`<!-- ... -->` 会留在源文件里，且在某些渲染器下被原样输出。禁止把唯一信息放进注释。
- 不用的内容直接删，不要注释掉；注释掉的内容不会被链接检查与拼写检查覆盖，只会腐烂。
- 生成内容（自动生成的目录、API 索引、表格）必须带生成标记与生成命令，禁止手改生成结果。
- front matter 用 YAML，只放机器要读的字段：`title`、`description`、`owner`、`status`；叙述性内容写正文。
- 引用式链接定义集中在文末或小节末，标签用小写 kebab-case，与链接文字区分。
- 图表、截图的替代文本写清“这张图说明了什么”，不写“图片”“截图”（`MD045`）；装饰图用空 alt 并标 `aria-hidden`。
- 需要保留但读者不该看到的信息，放到仓库的变更记录或 issue 里，不要靠 HTML 注释传递。

## 10 工具链与验证

- 规则检查：`markdownlint-cli2 "**/*.md"`（或 `markdownlint`），退出码非 0 即失败；配置写 `.markdownlint.jsonc` 并提交。
- 格式化：`prettier --check "**/*.md"` 校验、`prettier --write` 写入；Prettier 会重排列表缩进与换行，先确认它的 `tabWidth` 与 `proseWrap` 与仓库约定一致。
- 断链检查：`lychee --offline` 校验相对链接与锚点，联网检查外部链接；外部链接失败要区分“已失效”与“临时不可达”。
- 风格检查（可选）：`vale` 按术语表与语气规则检查；规则文件入库，避免个人配置导致结果不一致。
- 渲染验证：在目标平台预览表格、嵌套列表、代码高亮、锚点跳转；GitHub 的锚点规则是转小写、去标点、空格转换连字符。
- 代码块校验：围栏语言标签必须真实存在；示例命令在 CI 里至少执行一次，或标注为不可执行。
- 编辑器无关：`.editorconfig` 写 `charset = utf-8`、`end_of_line = lf`、`insert_final_newline = true`、`trim_trailing_whitespace = true`。
- 退出条件：markdownlint 0 错误、Prettier 无 diff、链接检查 0 断链、目标平台预览通过。
- 参考文档：[CommonMark 规范](https://spec.commonmark.org/)、[GFM 规范](https://github.github.com/gfm/)、[Google Markdown Style Guide](https://google.github.io/styleguide/docguide/style.html)、[markdownlint 规则表](https://github.com/DavidAnson/markdownlint/blob/main/doc/Rules.md)、[Write the Docs 风格指南索引](https://www.writethedocs.org/guide/writing/style-guides.html)。

## 11 反例（Good / Bad）

Bad：跳级标题、代码块无语言、链接文字无信息、表格列数不一致、行宽失控。

````markdown
# 部署

### 步骤

运行下面这段：

```
make deploy
```

点击[这里](https://example.test/deploy?utm_source=doc)查看细节。

| 环境 | 地址 | 备注 |
| --- | --- | --- |
| prod | https://example.test | 生产，发布前必须过变更评审并通知 oncall |
| staging | https://staging.example.test |
````

Good：单一 H1、层级只降一级、围栏都标了语言、链接文字自足、代码块在有序列表内正确缩进、文末给出下一步链接。

````markdown
# 部署

本页说明如何把 `api` 服务发布到生产环境。

## 前置条件

- 已通过 `make test` 与 `make lint`
- 有 `deploy` 角色的凭据

## 步骤

1. 构建镜像：

   ```bash
   make build IMAGE_TAG=local
   ```

2. 发布到预发并验证：

   ```bash
   make deploy ENV=staging
   ```

生产发布需要变更评审，流程见[发布评审清单](./release-review.md)。
````

Bad：可复制的字面量（文件名、字段名）裸写在正文里，读者分不清哪些该敲进终端；标题下也没有一句说明本文解决什么问题。

````markdown
# 配置

修改 config.yaml 里的 maxRetries 字段，然后执行

```bash
make reload
```

缓存会失效。
````

本节所有示例都套在四个反引号的围栏里：外层围栏必须比内容里出现的围栏长，否则内层三个反引号会提前关闭外层，示例被截断。

## 12 评审清单

- [ ] 单文档一个 H1，标题层级不跳级、不重复、不带句末标点，与文件名语义对应
- [ ] 行宽 ≤80（链接、表格、标题、代码块豁免），无尾随空格，无连续空行，文件末尾单换行
- [ ] 缩进宽度与仓库 `.markdownlint.*` 一致（4 空格或 2 空格），全文未混用
- [ ] 所有代码围栏标了语言，嵌套围栏的外层比内层长，围栏成对闭合
- [ ] 表格每行列数一致，前后各一空行，单元格只放短语
- [ ] 链接文字描述目标，未使用“点击这里/这里/链接/更多”，外部链接无跟踪参数
- [ ] 相对链接与锚点在目标平台实测可跳转，重命名后无遗留旧路径
- [ ] 代码示例可运行、上下文自足，示例输出与示例代码分块
- [ ] 术语、产品名大小写全文统一，首次出现给了全称与缩写
- [ ] 易过期信息（版本、日期、环境）集中在文末，未散落在正文
- [ ] `markdownlint` 0 错误、`prettier --check` 无 diff、链接检查 0 断链
- [ ] 接口或行为改动在同一 PR 内更新了对应文档

> 冲突时的裁决顺序：仓库 `.markdownlint.*` 与目标渲染器实测行为 → 同目录既有文档 → Google Markdown Style Guide → markdownlint 默认值；语法歧义以 CommonMark 规范为准，扩展语法以 GFM 规范与目标平台实现为准。
